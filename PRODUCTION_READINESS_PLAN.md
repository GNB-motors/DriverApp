## 1. Executive Summary & Roadmap

# DriverApp — Production Readiness: Executive Report

## 1. Executive verdict

**NO-GO for production. Readiness score: 3.5 / 10.**

The DriverApp is architecturally sound where it counts — a single centralized axios client, cleanly decoupled 401→logout handling, role-isolated navigation stacks, per-account state wiping, and Sentry wired in. But it is not shippable today. Two classes of defect are disqualifying: (a) a **silent demo-mode auth bypass** that activates whenever `EXPO_PUBLIC_API_URL` is unset — and no EAS build profile sets it, so a release binary defaults to fabricated data and password-less login; and (b) **missing iOS camera/photo-library usage strings + Android CAMERA permission**, which crash the core capture flows on device and guarantee App Store rejection. Layered on top: the JWT and full user PII sit in plaintext AsyncStorage (unacceptable for a wallet/money app), there is no React error boundary (any render throw white-screens a driver mid-route), three upload flows silently discard user data, and the shipped hi/bn i18n is wired into only 2 of 56 screens. The foundation is good; the release surface is not safe. Roughly 3–4 weeks of focused P0 work stands between this build and a defensible pilot.

## 2. Top production blockers (P0)

Ranked by release risk:

1. **Demo-mode auth bypass ships in production** — `apiConfigured()===false` silently routes any input to `demoLogin()` with a hardcoded `demo-token` and elevated roles (known numbers → OWNER/MANAGER, anything else → DRIVER), no password check. `eas.json` sets no `env` for any profile, so this is the *default* state of a shipped build, not a corner case. **Blocks because:** a misconfigured release is a complete authentication bypass indistinguishable at runtime from a working app. **Effort: S** (gate behind `__DEV__`/explicit flag + fail-closed; pin the URL in eas.json).

2. **iOS camera/photo strings + Android CAMERA permission missing** — no `NSCameraUsageDescription`/`NSPhotoLibraryUsageDescription`, no `android.permission.CAMERA`, and the expo-image-picker/expo-camera config plugins aren't registered. **Blocks because:** first camera access hard-crashes on iOS and is rejected at App Store review; capture is core to fuel bills, POD, consignment notes, and documents. **Effort: S.**

3. **JWT + full user PII in plaintext AsyncStorage** — no expo-secure-store / Keychain / Keystore anywhere. A bearer token (with no expiry/refresh and no server-side revocation on logout) plus PII is readable via ADB backup, root, or forensic extraction. `allowBackup` also defaults true. **Blocks because:** for a money app this is the headline exposure and it makes the client-trust RBAC (role read from tamperable storage) exploitable. **Effort: M** (persistence is already isolated in `persist()`/`restore()`).

4. **No React error boundary** — `Sentry.wrap()` adds instrumentation only, not a fallback UI. Any render exception white-screens the app with no recovery for a driver on the road. **Blocks because:** it converts any single-screen bug into a total, unrecoverable app failure in the field. **Effort: S.**

5. **Silent data loss in three upload flows** — Consignment Note collects up to 3 pages but uploads only the first; the fuel bill photo is POSTed as JSON (never actually uploaded); repair photos are captured and dropped. **Blocks because:** drivers are told their evidence was submitted when it was not — a correctness and trust failure in the money/compliance path. **Effort: M** (route through the existing `postForm` multipart helper).

## 3. Cross-cutting themes

- **Config drives correctness (and security).** The single most damaging issues all trace to one unset env var: demo bypass, offline demo data, disabled Sentry (`EXPO_PUBLIC_SENTRY_DSN` also unset), and a README documenting a non-existent config file. The app *degrades silently* instead of *failing loudly* — the recurring anti-pattern.
- **Data-at-rest is unprotected end-to-end.** Plaintext token, plaintext user PII, plaintext debug logs (role + user IDs, never purged), `allowBackup` on, no screenshot/FLAG_SECURE protection on wallet/PII screens. No single secure-storage decision was made.
- **Failures hide as emptiness.** `useApi` captures `error` but no read screen renders it; offline (`ERR_NETWORK`) never hits the friendly-message branch; guessed API field names (`// mapping to confirm` in ~21 files) degrade to `—`/0. Users can't distinguish "broken" from "empty," and there's no pull-to-refresh or retry anywhere.
- **Built but not wired.** A recurring "capability exists, unused" pattern: full en/hi/bn dictionary (2/56 screens), `compressImage()` (never called), `EmptyState` error prop (used nowhere), `react-native-view-shot` (unused). Significant dead investment sitting one step from value.
- **Scale cliff is deferred, not avoided.** Zero list virtualization (every list is `ScrollView` + `.map()`) and zero pagination across all 16 services. Fine at pilot volumes, guaranteed jank/memory growth at fleet scale.
- **Client is treated as authoritative where the backend must be.** Role decides the rendered stack from tamperable storage; `X-Org-Id`/`X-Branch-Id` are client-supplied. Safe only if the backend enforces RBAC and tenancy from the verified token — must be confirmed.

## 3. Detailed Findings by Dimension

### File Handling & Device Permissions

The upload plumbing is clean and centralized (single axios client, a dedicated 60s multipart helper, quality-0.7 capture, remove/max limits in the PhotoUploader), but the audit surfaces several serious gaps. Most critical: app.json declares NO iOS camera/photo-library usage-description strings and NO Android CAMERA permission, and the expo-image-picker/expo-camera config plugins are absent — this will crash the camera flow on iOS (and App Store reject) and break capture on Android. Permission denial is handled gracefully (no crash) but silently — a driver who denies camera access just sees nothing happen, with no explanation or open-settings prompt. There is no client-side file size/type validation, no image downscaling (the compressImage util exists but is never called, so full-resolution multi-MB photos are uploaded over driver mobile data), and no upload-progress feedback. Three flows silently lose data: the Consignment Note screen collects up to 3 pages but uploads only the first; the fuel bill photo is passed to a JSON endpoint and never actually uploaded; and repair photos are captured but never sent. Upload failures ARE surfaced in the Bill/POD/CN flows via useSubmit + WarningBanner, which is good, but the app cannot detect the noted backend S3 silent-'success' case.

### Mobile Security & Secrets (DriverApp/frontend — Expo SDK 54 / RN 0.81 / React 19)

### Performance & Scalability (client)

The DriverApp frontend (Expo SDK 54, RN 0.81, React 19) renders every list through ScrollView + Array.map() — there is zero list virtualization anywhere in the codebase (grep for FlatList/SectionList/FlashList returns nothing).
